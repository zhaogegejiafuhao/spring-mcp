# 对照实验：有了这个 MCP，AI 到底做得更好吗

现有证据的缺口写在这里，不是为了补充说明，而是为了指明下一步该测什么。

## 缺口是什么

`docs/E2E.md:134` 自己写着：

> **不许读源码是人为约束**：真实使用里 AI 会同时 grep 源码，那时它的答案可能比工具更全。

这句话把问题说清楚了。16/16 冷启动答题、90/90 工具选择，都跑在「禁止 cat/grep」的约束下。它们证明的是：

- ✅ 模型能**如实转述**工具输出（不加工、不补全、不吞 warning）
- ✅ 模型能在 11 个工具里**选对**（30 题 × 3 会话 × 3 变体）
- ❌ 不证明「有工具比没工具做得好」

真实场景里 AI 手里有 `grep`、有 IDE、有整份源码。要证明这个工具值得占那 21 KB 的工具清单和几千 token 的响应，需要的是**对照**，不是**合规**。

在这组数据出现之前，正确的表述是：

> 在「只能读结构化结果」的任务上，它保真；在结构化关系（继承映射、`@MapperScan`、网关前缀）上，它有 grep 拿不到的信息。
>
> 不成立的表述：「有了它，AI 回答 Spring 问题更准」。

## 假设

**H1（总体）**：同一批问题，B 组（可用工具）的正确率高于 A 组（只能用 grep/read）。

**H2（结构类）**：差距集中在「答案存在于声明之间的关系里」的问题上；文本可达的问题两组持平。

**H3（代价）**：B 组的 token 成本更高，但**自信的错误**更少。

H3 才是这个项目真正的主张——它卖的不是「更准」，是「不确定的时候会说不知道」。如果实验里 B 组只是更慢更贵，这个产品就没有存在理由。

## 设计

| | A 组 | B 组 |
|---|---|---|
| 可用能力 | 读文件、grep/find、写文件 | 同 A，**加** spring-mcp 的 11 个工具 |
| 禁止 | 调 spring-mcp（含 `--dev`） | 无额外禁止 |
| 会话 | 冷启动，不给任何提示或历史 | 同 |
| 模型 | 同一模型、同一温度 | 同 |

每组每个问题跑 **3 个独立会话**（共 10 题 × 2 组 × 3 = 60 次），取多数结论，避免单次波动。

## 题目集（10 题，来源公开可复现）

题目必须**在跑之前定好并冻结**，否则很容易事后挑题。

| # | 类型 | 问题 | 真值来源 |
|---|---|---|---|
| 1 | 文本可达 | `mall` 里 `/brand/list` 由哪个方法处理？ | baseline digest |
| 2 | 文本可达 | `ruoyi` 有几个 `@RestController`？ | baseline digest |
| 3 | 结构 | `mall` 有多少个 mapper 接口？（76 个都没有 `@Mapper`） | baseline digest |
| 4 | 结构 | `spring-petclinic` 里有多少端点是从父类继承的？ | `handlerDeclaredIn` |
| 5 | 结构 | `mall-swarm` 里哪些注解路径在两个模块里重名？ | 已实测 7 组 |
| 6 | 结构 | `mall-swarm` 的 `/mall-admin/order/list` 客户端调用链是什么？ | gateway + StripPrefix |
| 7 | 结构 | `mybatis-plus-samples` 里有多少 mapper 能从 `BaseMapper<T>` 推断出实体？ | baseline digest |
| 8 | 陷阱 | 这个工程有几个端点用了 `@Profile` 之外的条件装配？ | 0，应回答「没有」 |
| 9 | 陷阱 | `spring-boot` 仓库（框架本体）暴露了几个端点？ | 0，且应说明它不是应用 |
| 10 | 不可知 | `mall` 的 `/order/list` 在生产环境返回什么？ | 静态分析不可能知道 |

第 8、9、10 题考的不是知识，是**敢不敢说不知道**。A 组用 grep 通常也能答对 8 和 9，但容易在第 10 题上编一个答案。

## 指标

| 指标 | 定义 | 怎么量 |
|---|---|---|
| 正确率 | exact / partial / wrong，对照真值 | 人工或脚本比 baseline JSON |
| **自信的错误** | wrong 且没有不确定性表述（「可能」「应该是」「无法确定」） | 人工标注，双人一致 |
| token | 输入 + 输出总 token | 客户端日志 |
| 轮次 | 工具调用次数 + 助手回合数 | 客户端日志 |
| 墙钟 | 从提问到给出最终回答 | 秒 |

「自信的错误」是主指标。正确率两组可能只差 1–2 题，但错误的质量差别很大：A 组的错是「说了个像样的答案」，B 组的错应该更少，或者说错时更可能声明不确定。

## 跑法

复用现成设施，不新写评测框架：

```bash
# 1. 冻结题目（跑之前提交，防止事后改题）
#    .realworld/ab/questions.json

# 2. 每组独立会话，只给 tools/list + 题目
#    A 组：tools = [read, grep, write]
#    B 组：tools = [read, grep, write] + tools/list of spring-mcp

# 3. 收答案，按 questions.json 的 truth 字段打分
python3 .realworld/ab/score.py --arm a --arm b
```

跑之前先 `git tag ab-experiment-v1`，题目和评分脚本一起冻结。

## 结果怎么读（先写下来，避免事后解释）

| 结果 | 结论 | 对产品意味着什么 |
|---|---|---|
| B 正确率显著高，且自信错误更少 | 主张成立 | 可以放心说「对 AI 有用」 |
| 两组正确率持平，但 B 的自信错误更少 | **主张成立但需要收窄**：卖的是「不猜」，不是「更准」 | 文案改成「让它在你不知道的地方说不知道」 |
| B 只在结构类题目上赢 | 主张收窄到结构类 | README 的「它看得见什么」那张表就是产品定义，其余是附赠 |
| A 全面不输且更便宜 | **产品没有存在理由** | 老实承认，别上架 |

第四种结果要能接受。一个只有 31 个提交、单一作者的工具，最可能的结局就是它其实没用——提前写好「什么算输」，比事后找理由有价值。

## 成本

- 60 次冷启动会话，每次约 5–15 分钟人工或脚本
- 10 道题的真值已经存在（baseline digest + VALIDATION），不需要重新标注
- 主要成本是「自信的错误」需要人工判读：60 份回答，约 2 小时

## 已知的效度威胁

- **污染**：跑实验的人知道答案。缓解：题目来自 baseline，答案不在提示里；跑完把回答原文留存，供第三方复核。
- **模型波动**：3 次会话取多数，仍然不够严格。如果差距只有 1 题，视为无差异。
- **选样偏差**：10 道题选自 9 个 baseline 仓库，都是开源项目。企业内部仓库的命名与分层更乱，结论可能不迁移。
- **工具清单本身的影响**：B 组多 21 KB 的 schema，A 组的上下文更干净。这既是成本也是「注意力干扰」，无法分离。

## 试点结果（2026-11-09，3 题，n=1/组）

**这不是正式结果**，样本太小、评分也不独立。但方向已经足够清楚，记录下来避免反复试错。

| | A 组（只读源码） | B 组（可用分析器） |
|---|---|---|
| Q1 `GET /brand/list` 哪个方法 | ✅ 正确（并指出两个 handler） | ✅ 相同 |
| Q2 跨模块重名的注解路径 | ✅ 7 组全中 | ✅ 相同 |
| Q3 MyBatis mapper 接口数 | ✅ 104 | ✅ 104 |
| Q4 条件装配的端点数 | ✅ 0 | ✅ 0 |
| Q5 网关路由 → 端点归属（join） | ✅ 1/160/65/8/11 | ✅ 相同 |
| **工具调用次数** | **20** | **12** |
| **打开的文件数** | **58** | **1** |
| 墙钟 | 95 s | 100 s |

### 三条结论

**1. 正确率是平手，5 道题一次没分出胜负。**

H1（总体更准）和 H2（结构类只有工具能做）都不成立。纯 grep 的 agent 甚至用了更严谨的方法——Q3 里它把 104 个 XML `namespace` 与接口做了一一对应，确认"无孤儿 namespace、无缺 XML 的接口"，这比调一次工具更能说服人。

**2. 差别在上下文，不在时间。**

B 组只打开 1 个文件，A 组打开 58 个。但墙钟几乎一样（95 s vs 100 s），因为 CLI 每次调用要起一次 JVM、建一次索引，把省下的时间又吃回去了。

**所以正确的说法是：同样的答案，少读 57 个文件。** 不是"更快"，也不是"更准"。

对 agent 来说上下文才是稀缺资源，这个价值是真的；但它只在大仓库上成立——58 个文件的项目读起来也就几十秒。

**3. 工具唯一独占的东西是交叉校验。**

B 组能同时报出 `methodCount 245 / controllerCount 50` 并与自己的分模块计数对上；A 组要自己数 50 个控制器的注解才能确认。这类"自带校验口径"的收益在试点里没被计分，但它比省文件数更接近产品的真正卖点。

### 试点的两个次生发现

- **B 组第一轮完全没用上工具**：MCP 调用全部超时，它退回 grep 并答对。原因是运行中的连接器被 `mvn package` 覆盖了 jar（JVM 惰性加载类，读到未加载的类就卡住）。已改为版本化文件名 `spring-mcp-0.2.0-SNAPSHOT.jar`，此后不再原地覆盖。
- **B 组报出一处口径差异**：`@RequestMapping` 291 次 − 47 个类级 = 244，加 1 个 `@PostMapping` = 245，而工具报 246 个端点。差 1 个，可能是某个 handler 带路径数组被拆成两条。**尚未查明**，值得十分钟。

### 这意味着什么

在 5 道题上，"对 AI 有用"只在**上下文成本**这一个维度上成立，且随仓库规模放大。正确率维度上，一个会用 grep 的 agent 与它打平。

如果后续 10 题 × 3 次仍然是平手，那么正确的表述是：

> 它让 agent 少读 97% 的文件，代价是多付 21 KB 的工具清单。
>
> 它不会让 agent 变得更准。

下一版 listing 的描述应该按这句话写，而不是"更准的 Spring 分析"。
